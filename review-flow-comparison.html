Interactive review · rendering paths

Approve / deny flow: experimental API vs. stable API

The same two-line change, reviewed two ways. Both flows accept or reject a single hunk — the difference is where the controls live and what draws them. That difference decides whether the extension can ship to the Marketplace.

These are faithful mockups, not live screenshots. They're reconstructed from the extensions' actual rendering code — hunkwise's decorationManager.ts (the inset button bar & red deleted-block) and diffCodeLens.ts (the CodeLens actions) — styled in VS Code's own theme tokens. A headless environment can't run VS Code to capture the real thing.

Stable API

Marketplace-safe · Cline / Continue / hunkwise fallback

Actions are CodeLens — clickable text links VS Code renders on their own line above the hunk. API: vscode.CodeLensProvider (stable).

What you're seeing: a native diff view (removed + added lines), with accept/discard as text-link CodeLens on a dedicated line. Plain, keyboard-reachable, and shippable — but the actions sit on their own line and can't float over the code.

Experimental API

Proposed · hunkwise default

Actions are a floating button bar; deleted lines render as a webview block — both inside the normal editor. API: editorInsets (proposed, #85682).

What you're seeing: you stay in the real file. Removed lines appear as a red inline widget and the accept/discard buttons hover right on the hunk — the slicker feel. Cost: it uses a proposed API, so no Marketplace.

Where they diverge

Same capability set (per-hunk accept/reject, auto-advance, multi-file). These are the deltas that actually matter.

Takeaway for us: the stable path delivers the full review-flow capability and can ship. The experimental path only adds inline polish — the floating buttons and in-buffer deleted block. Recommended: build on the stable path, keep editorInsets as an optional enhanced mode.
